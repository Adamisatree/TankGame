# 1.6.4 —— 座位耗尽（团队凑不齐）+ 本地日志

1.6.3 发布后收到两条反馈：

1. **团队模式进不去**（凑不齐人，房间明明空着却提示满员）；
2. **单人 / 团队进去后卡在背景图**，看不到坦克，也没有报错。

第 1 条可以复现，而且比报告里说的更糟（有两处 bug，见下）。第 2 条在本机无头环境里
**没有复现**——所以这一版的重点是：把它变成「下次一定能抓到」的问题，并且在它发生时
**不再把玩家留在背景图上**。

---

## 一、P0：座位耗尽（团队进不去的真正原因）

### 1.1 保留位被当成「已占用」

`server/lan-server.mjs` 的 `nextSeatId()`：掉线的座位会在 `room.sessions` 里保留
**2 分钟**，好让重连的人回到原座。v1.6.2 把「座位溢出发 p11」改成「拒绝加入」时，
把**保留位也算成了占用**：

```js
if (room.players.has(id) || reserved.has(id)) continue;   // ← 保留位 = 有人在？
return null;                                              // ← 于是直接拒绝
```

一个晚上正常玩（有人退出、有人换人、有人掉线重连），2 分钟内很容易攒满 9 条保留记录。
之后**所有新访客都被拒**，服务器日志只有一句 `every seat is taken`，而房间里实际只有房主。
触发之后要等 2 分钟 TTL 才恢复——正好表现为「团队凑不齐人 / 房间满了但没人」。

### 1.2 更隐蔽的第二处：座位号算到了 p11

```js
for (let seat = 2; seat < SEAT_LIMIT + 2; seat += 1)   // SEAT_LIMIT = 10 → 2…11
```

`p11` 是**不存在的座位**：客户端的配色表（`Tank.ts`）、输入路由（`GameScene` 的
`p3…p10`）都只到 p10。平时这条路径被容量检查挡住（`players.size >= capacity` 先拒绝），
但「保留位占满、真人很少」时恰好能走到它——访客拿到 p11，房主那边**没有它的坦克、也没有它的输入行**，
于是就是「进来了但什么都看不见」。实测确认（见下）。

### 1.3 修法

- **容量是唯一的硬闸**：`nextSeatId()` 只在座位被**在场玩家**占满时返回 null；
- 座位全被**保留位**占住时，把「最久没回来」的那条保留记录让给新人（重连回到原座本来就是尽力而为，
  TTL 到期也一样会丢），房间再也不会假满员；
- 座位号范围改成真正的 `p2…p10`（`seat <= SEAT_LIMIT`）。

拒绝原因也收敛了：`full` 现在**只**表示「座位都被在场的人占着」。

### 1.4 回归测试（lantest 118 → 126）

新增场景：容量 10 的房间，**10 个访客先后进/出**（制造 10 条保留位），然后

| 检查 | 修复前 | 修复后 |
| --- | --- | --- |
| 十次进出不会中途没座 | ✅ | ✅ |
| 重复使用那 9 个真实座位 | ❌ `p2…p11` | ✅ `p2…p10` |
| 没有发出 p2…p10 以外的座位 | ❌ 出现 `p11` | ✅ |
| 空房间仍能给新人座位 | ❌ `reject: full` | ✅ |
| 新人的座位来自保留位 | ❌ `undefined` | ✅ |
| 房主看到的是「自己 + 新人」 | ❌ 只有 `p1` | ✅ |
| 真满员时仍然拒绝 | ✅ | ✅ 理由 `full` |

反向验证：把旧的 `nextSeatId()` 放回去，上面 5 条立刻变红（`121/126`），
其中一条正是玩家看到的「房间里只有房主，却被 `full` 拒绝」。

## 二、本地日志（安装目录 `log\`）

### 2.1 玩家会看到什么

```
<安装目录>\resources\app\log\
  tankgame-main.log      主进程：启动、崩溃、局域网服务、渲染冻结
  tankgame-renderer.log  渲染进程：JS 异常、未处理的 Promise、上一轮的遗留错误
  tankgame-server.log    局域网服务：监听、拒绝、断开、停止
```

- 单个文件超过 **512 KB** 自动改名为 `tankgame-<时间戳>.log`，最多保留 **5** 个历史文件；
- 安装目录不可写（装在 `C:\Program Files`、只读 U 盘）→ 自动回退
  `%APPDATA%\TankGame\log`，并在第一行写明回退原因；
- 浏览器 / 单文件版没有文件系统：错误进 `localStorage` 环形缓冲（最近 50 条），
  下一次启动折进日志。

### 2.2 三类事故各自的取证

| 事故 | 落点 |
| --- | --- |
| 主进程抛异常 | `tankgame-main.log` 的 `[main-crash]` + 完整 stack，**先落盘再退出**（退出码 1，和默认行为一致） |
| 渲染进程抛异常 / Promise 拒绝 | `tankgame-renderer.log`（`window.onerror` / `unhandledrejection`） |
| **画面卡死**（没有任何异常） | 渲染进程每秒发心跳（带 `phase` / 坦克数 / 暂停 / 模式）；超过 **12 秒**没心跳，主进程写 `[freeze] renderer silent for Ns — last state: phase=playing tanks=5 …` |
| 局域网拒绝 / 断开 | `tankgame-server.log`：`refused guest: room full 10/10`、`guest p3 joined (3/4)`、`p3 disconnected`… |

「卡在背景图」这类问题，下一次会直接变成一行：

```
[freeze] renderer silent for 12s — last state: phase=ready tanks=0 paused=false matchOver=false mode=solo role=-
```

——`tanks=0` + `phase=ready` 说明场景 `create()` 没走完（不是卡在更新循环里），这就是要的信息。

### 2.3 实现要点

- 新增 `electron/log.cjs`（纯 Node，可单测）：`createLogger({ dir, fallbackDir })` →
  `write(stream, line)`；**任何失败都吞掉**（磁盘满、文件被占用、参数是垃圾），
  日志系统绝不能成为第二次崩溃的原因；
- `electron/main.cjs`：启动即写一行（版本 / 平台 / Electron 与 Node 版本 / 日志目录），
  注册 `uncaughtException`（写盘后 `exit(1)`）与 `unhandledRejection`，3 秒一次看门狗；
  新增 IPC `log:write` / `log:heartbeat` / `log:path` / `log:reveal`；
- `electron/preload.cjs`：`tankGame.log` 四个方法，字段白名单 + 长度截断（渲染进程不能塞任意内容）；
- `src/log.ts`（新）：错误钩子、每秒心跳、上一轮错误合并、日志目录查询；桌面走 IPC，
  浏览器走 `localStorage`；
- `server/lan-server.mjs`：`createLanServer({ logLine })`（桌面）或 `{ logFile }`（独立运行），
  在监听 / 拒绝 / 加入 / 断开 / 停止处各写一行；
- `electron/lan-boot.cjs`：把 `logLine` 透传给服务器，写进同一个 `log\` 目录。

### 2.4 这一版最该有的那个测试

`desktop-test` 里新增的一步会**真的让主进程崩一次**（子进程里抛 `boom-from-test`），然后断言：

```
  ok   an uncaught exception is written to the log
  ok   the app still dies after logging it
```

此外还覆盖：写入 / 时间戳、512 KB 轮转、历史文件只留 5 个、安装目录不可写时回退并记录原因、
日志接口喂垃圾也不抛。

## 三、「卡在背景图」：不再把玩家留在那儿

无头环境没能复现，所以我们做了两件事——**让它可诊断**（上一节），**让它可恢复**（本节）。

1. **开局看门狗**：点「开始游戏」后，主界面隐藏、场景启动。如果 2 秒内场景没有报告
   `booted`（`create()` 的最后一行），或场景根本没起来，就弹出错误卡：
   出了什么错、日志在哪个目录（桌面版还能一键打开），以及两个按钮；
2. **兼容模式**：错误卡上的「用兼容模式重开」把渲染器从 WebGL 切到 Phaser 的 Canvas
   （`localStorage.tankduel.renderer = 'canvas'`），重新加载。显卡驱动导致的白屏 / 卡死
   是这类症状最常见的成因，这个开关能把人救回来；
3. `startMatch()` 本身包了 try/catch：抛异常时直接进错误卡，而不是「点了没反应」。

## 四、顺带

- **拒绝原因说人话**：`full` → 「房间满了（最多 N 人），等有人离开再试」；
  `unknown` → 「房主不在房间里，稍后再试（或问一下房主的地址）」。以前一律是「房间拒绝了这次连接」。
- **复核 1.6.2 的三项修复**（报告第六节要求）：
  重连继承血量（`a reconnect comes back to the tank it left`）、
  换图清 `startPending`（`switching the room map forgets a pending start`）、
  房主离开横幅（`B-12`）——都在 `smoke` 里，本轮 180/180 通过。

## 六、兼容

协议格式没变（仍是 v11），版本闸门按版本号比对：**1.6.3 与 1.6.4 不能联机**。

## 七、真机自查

1. 团队 4 人开局 → 打完一局，全部退出 → **再让一个人加入**（必须能进，不再提示满员）；
2. 同一房间反复进出 10 次 → 每次都拿到 p2…p10，房主能看到每台坦克；
3. 点「开始游戏」后若只看到背景图：等 2 秒，应弹出错误卡 → 点「打开日志目录」，
   把 `tankgame-main.log` / `tankgame-renderer.log` / `tankgame-server.log` 发回来；
4. 点「用兼容模式重开」→ 能正常进游戏（说明是渲染后端的问题）。
