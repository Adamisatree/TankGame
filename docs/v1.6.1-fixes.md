# 1.6.1 —— 多人联机：谁控制哪台坦克

玩家报的四个症状——**人一多就有人卡死动不了 / 像顶号 / 基本只有 2 个人能同时动 / 团队开不了局**
——不是四个 bug，而是 **一个根因 + 两个放大器**。这一版三个都修了，并把「座位变动之后
再发输入」这条从没被测过的链路补进了自动化套件。

---

## 一、根因：输入按「槽位」路由，而不是按「座位 id」

房主场景里远程坦克存在两个地方：

| 存放位置 | 谁在里面 |
| --- | --- |
| `this.p2` | **第一台**远程坦克（历史原因：1v1 时代只有它） |
| `this.extras` | 其余所有远程坦克 |

这个槽位会**换人**：`removeRemoteTank()` 删掉 p2 槽位的坦克时，会把 `extras` 的第一台**晋升**进去；
重连的访客也会被重新创建到有空位的地方。

而输入以前是这么分发的：

```ts
// 旧代码
onInput: (input, from) => {
  if (from === 'p2' || !this.byId(from)) {   // ← 特例
    this.remoteInput = input;                // ← 只有这一个字段
    ...
  }
  this.remoteInputs.set(from, input);
}

// 每帧
if (this.p2) this.applyInput(this.p2, this.remoteInput, ...);   // p2 槽位吃 remoteInput
for (const tank of this.extras) this.applyInput(tank, this.remoteInputs.get(tank.id) ?? IDLE_INPUT, ...);
```

**槽位里的坦克 id 一旦不是 `p2`**（晋升/漂移之后必然如此），它的输入就再也没人读：

- 槽位里现在是 p3 的坦克 → 它只吃 `remoteInput`（p2 的残留输入）→ **没人操作它自己会转（幽灵）**，
  而 p3 真按的键进了 `remoteInputs`，没有任何代码读它 → **p3 卡死**；
- 重连回来的 p2 被建到 `extras` 里 → 它的输入落在 `remoteInput`（因为 `from === 'p2'`），
  于是 **p2 在开 p3 的坦克（顶号），自己的坦克不动（卡死）**。

这正是「基本只有 2 个人能同时动」（只有 p1 和「真正坐在 p2 槽位的那一位」能动）与「像顶号」。

### 修法

```ts
// 新代码：只按 id
onInput: (input, from) => { this.remoteInputs.set(from, input); }

private applyRemoteInput(tank: Tank, dt: number): void {
  const input = this.remoteInputs.get(tank.id) ?? IDLE_INPUT;  // ← 坦克自己的 id
  this.applyInput(tank, input, dt, { aimRate: 22 });
  if (input.skill) { input.skill = false; this.useSkill(tank); }
}
```

`this.p2` 槽位和 `extras` 现在只是**存放位置**，与「谁控制它」完全无关；单人与本地双人走的是
`readLocalInput` 分支，不受影响。另外 `removeRemoteTank()` 会同时删掉该座位的输入行——座位号
现在会被后来的新玩家复用，残留的按键不能跟过去。

**实测**（真实服务器 + 真实房主场景 + 真实 WebSocket 访客）：

| 场景 | 修复前（车身累计转角） | 修复后 |
| --- | --- | --- |
| p2 中途退出、p3 被晋升后无人操作 | p3 **自己转了 2.05 rad** | 0.00 |
| 晋升后 p3 按自己的键（右 / 左） | **+1.74 / +1.68**（两个方向都只往右，完全不受控） | +1.46 / −1.46 |
| p2 重连后按自己的键 | **0.00（卡死）** | 1.46 |
| p2 重连后按自己的键，看 p3 的坦克 | **+1.48（顶号）** | 0.00 |

## 二、放大器 1：座位号只增不减 —— 第二局必现「有人开局冻结」

服务器的座位号来自一个只增不减的计数器（`p${room.nextId++}`），而房间清空时**没有复位**。
于是同一个服务器进程里：

```
第一局：访客拿到 p2、p3
人走光 → 房间空掉 → 计数器还停在 4
第二局：新访客拿到 p4、p5   ← 没有任何断线
        p2 槽位里是 p4 的坦克，但 p4 的输入不会进 remoteInput
        → 第一个加入的访客从开局第一帧就不会动
```

这就是「多一点人就有人卡死」的另一半：不需要任何人掉线，**第二轮对局开始就会出现**。

### 修法

- **房间空掉即复位**：`nextId` / `teamCount` / `mode` / `capacity` / `config` 全部回到初始值；
- **分配最小的空闲座位号**（`nextSeatId()`），而不是递增计数器 —— 房间开一整天，座位号也始终
  落在 p2–p10，不会漂到 p13 / p14（那还会让座位颜色退化成同一个颜色）；
- 掉线玩家的号码在 `SESSION_TTL_MS`（2 分钟）内**仍为他保留**，新人抢不走，重连一定回到原座。

## 三、放大器 2：空房间记着上一局的队伍数 —— 团队模式开不了局

`room.teamCount`（房主在房间里加的队伍数）只有 `teams` 消息会写，房间清空时没有复位。
上一局设了 4 队，下一局只有 3 个人 → 第 4 队永远是空的 → 服务端 `begin` 直接拒绝
（`lobby-error: empty-team`），客户端「开始对局」按钮同时置灰并提示「第 4 队还没有人」。
**换人也没用**，因为这个状态在服务器里，只能重启服务。

### 修法

并入上面的「房间空掉即复位」。实测：

```
修复前：round2 teams=4 → 3 人团队开局 → REFUSED [1,1,1,0]
修复后：round2 teams=2 → 3 人团队开局 → ok
```

单人和乱斗不受影响。**begin 的「每队至少 1 人」校验本身没有动**（那是 v1.5.2 修过的正确行为）。

## 四、测试缺口：为什么全套自动化全绿还是漏了

原来的检查里：

- smoke 的 p3/p4 冷却检查**绕过网络**直接调 `applyInput`，从没走过「座位变动 → 再发输入」；
- lantest / multitest 只验证**服务器**的座位分配与转发，不验证**房主场景**里输入落在哪台坦克上；
- 没有任何用例覆盖「p2 退出后被晋升的座位」「第二局的座位号」「重连后的输入归属」。

这一版补了 **18 条**（smoke 147 → 156，lantest 71 → 80）：

**smoke（9 条，真实 LAN 服务器 + 真实房主场景 + 真实 WebSocket 访客）**
1. 三个访客分别拿到 p2 / p3 / p4；
2. 房间进入对局；
3. **每个远程座位都能驱动自己的坦克**（「只有 2 人能同时动」的稳态基线）；
4. 有人退出后 p2 槽位被补上（槽位确实换人了，才谈得上后面的回归）；
5. **晋升后的坦克不会被离开者的残留按键带着走**；
6. **晋升后的座位仍保留自己的操控**（左、右都测）；
7. 重连的访客回到原座位；
8. **重连的访客只驱动自己的坦克**；
9. **并且操纵不了别人的坦克**。

**lantest（9 条，纯服务器）**
1. 第一局发出 p2 / p3；
2. 房主可以把队伍数调到 4；
3. **第二局重新从 p2 开始编号**；
4. **空房间忘掉上一局的队伍数**（回到 2）；
5. **空房间忘掉上一局的容量**（回到 6）；
6. **3 人团队局在第二局能正常开局**；
7. 掉线的座位号码被保留；
8. 新人抢不走它；
9. 本人重连仍回到 p2。

**这些断言在旧代码上实测会红**——把旧逻辑放回去重跑：smoke 挂 4 条、lantest 挂 6 条，
换回新代码即全绿。不是「跑绿了就算」。

## 五、顺带

`smoke` 的「AI 开局保护期」原来用 `aiGraceUntil > now` 精确比较。机器忙时 Phaser 的场景时钟会
大步跳跃，刚授予的保护期一眨眼就被判成「没有保护期」——高负载下偶发假红（与本版改动无关）。
现在改成容差断言：检验的是**曾经给过保护期**，而不是「一毫秒都没过去」。

## 六、协议与兼容

线上格式没有变化（`PROTOCOL_VERSION` 仍是 **11**），但应用版本变了，服务器的版本锁按版本号比对：
**1.6.0 与 1.6.1 不能联机**，请和朋友一起更新。
