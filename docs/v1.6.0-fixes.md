# 1.6.0 —— 代码审查整改

1.5.4 发布之后做了一轮完整审查：干净 clone `origin/main`、重装依赖、跑完整测试矩阵、
逐文件对比重构前后的 diff。这一版把审查里**全部 5 条**发现都处理掉，并为每一条补了
可复现的自动化检查。**没有新玩法，只有正确性和稳定性。**

---

## 问题 1（中等）｜重连成功后清空 `pending`，拨号窗口内的控制消息被静默丢弃

**以前**（`src/net/LanClient.ts`）：`write(msg, true)` 会在 socket 还没 OPEN 时把控制消息
压进 `pending`，等握手成功后补发。但 `ws.onopen` 一进来就先 `this.pending.length = 0`，
把**本次拨号期间**排队的消息全删了，紧接着的 flush 循环永远拿到空数组（死代码）。
那句注释的理由「上一个 socket 的残帧属于死连接」只对**上一次**拨号成立。

**真实后果**（都是玩家可见的「点了没反应」）：

| 场景 | 结果 |
| --- | --- |
| 访客在重连窗口（0.8–5 s 重试间隔）点**准备 / 选技能 / 换队** | 房主永远看不到，要再点一次 |
| 房主在重连窗口点**开始对局 / 换地图 / 改规则** | 房间毫无反应 |
| 房主在断线期间点**再来一局** | 访客永远停在上一局的结算卡上（v1.5.0 修过的回归路径） |

**现在**：清空动作挪到 `connect()` 的开头（新一次拨号开始时就丢掉上一条死连接的残帧），
`onopen` 恢复「先 join，再按顺序补发本次拨号期间排队的消息」。`close()` 仍然清空队列，
所以主动退出后不会再补发。

**验证**（`smoke`）：「a message queued mid-dial is delivered after the handshake」——
`connect()` 之后立刻 `send({t:'restart'})` + `setReady(true)`，断言服务端两条都收到；
「a closed client does not keep a backlog」——`close()` 之后不再补发。
（把旧代码放回去，第一条会只剩 `join`，实测复现。）

## 问题 2（低）｜`routeSnapshot` 用 `Date.now()` 判断快照节奏

**以前**：合并逻辑靠「两帧间隔 ≥ 20 ms」区分正常流和积压洪泛，时钟源是 `Date.now()`。
Windows 上系统定时器粒度约 **15.6 ms**，与 20 ms 阈值同量级：真实的 18 ms 间隔可能被读成
0 ms（误判洪泛、白等一个 20 ms），正常的 30 Hz 流也可能被读成 15.6 ms（正常流被折叠）。
浏览器里 rAF 会打开高精度计时器所以通常看不出来，但这是**环境依赖的正确性**问题。

**现在**：改用 `LanClient.clock()` → `performance.now()`（单调、亚毫秒；浏览器 / jsdom /
Node 都有，缺失时回退 `Date.now()`）。顺带的好处：玩家改系统时间也不会影响合并窗口。

**验证**（`smoke`）：「a frozen wall clock does not delay a live stream」——把 `Date.now`
钉成一个常量，模拟最坏情况；断言 6 帧 30 Hz 流**每一帧都是到达即应用**，不绕 20 ms 合并通道。
（换回 `Date.now()` 实测 0/6，复现。）

## 问题 3（低 · 测试脆弱点）｜背压测试与服务器 15 秒心跳竞态

**以前**：两个背压场景用 `ws.pause()` 停掉客户端读通道来制造积压——同时也就停掉了
ping/pong。若机器很慢让整块跑过两个心跳周期（约 30 s），服务器会先把这条连接当死连接
清掉，「落后访客仍然收到关键帧」就会假红。

**现在**：心跳间隔可注入 —— `createLanServer({ heartbeatMs })`（生产仍是 **15 s**），
测试里传入 `10 分钟`，背压逻辑与被测代码保持独立。类型声明同步更新。

**验证**：用 `heartbeatMs: 300` 实测，停读的客户端约 0.6 s（两个周期）后被正常清掉，
说明注入生效；`lantest` 的两个背压块改用长心跳后稳定通过。

## 问题 5（加固）｜服务器 `close()` 只有一条完成通路

**以前**：只等 `wss.close → server.close` 这条回调链——链上任何一个 socket 卡在关闭握手里，
退出就要等满 **2 秒兜底**；在 Node < 18.2 上，对已关闭的 server 再 `close()` 会**同步抛错**，
而那个抛错恰好发生在 `wss.close` 的回调内、无人接，于是这条链彻底失效。

**现在**：

- `finish()` 幂等，内部自己 `clearTimeout(guard)`；
- `server.once('close', finish)` —— HTTP server 一关就完成，不再依赖回调链；
- `closeAllConnections()` 与 `server.close()` 各包一层 try/catch，兜住低版本 Node 的同步抛错；
- 2 秒硬上限保留，作为最后的保险。

**验证**（`lantest`）：除了原有的「closing the server is bounded（<3000 ms）」，
新增「closing the server is quick on the normal path（<1000 ms）」——确认正常路径走的是
真实完成信号，而不是烧掉兜底计时器。
