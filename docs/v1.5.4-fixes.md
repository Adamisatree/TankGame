# 1.5.4 —— 联机「一直卡住」专项

「联机老是卡住」不是一个 bug，是 **5 个独立根因**叠出来的同一副症状：画面定格、
追不上房主、房主切后台全房停摆、网络一抖就出局、房主刷新页面整间房散伙。
这一版把 5 个根因全部修掉，另修两个会导致「各打各的地图」和「进程退不出去」的隐蔽问题，
并加了 12 条自动化检查防回归。

---

## 一、根因 1：一次失败的发送，冻住整个游戏（最常见）

**以前**：浏览器 WebSocket 进入 CLOSING / CLOSED 后调用 `send()` 会抛
`InvalidStateError`；而「检查 `readyState` → 真正 `send()`」之间有一个竞态窗口。
房主每秒发 30 次快照、访客每秒发 30 次输入，只要撞上一次，异常就从
`LanClient.send*()` 一路穿出 Phaser 的 `update()`，**requestAnimationFrame 循环直接终止**
——画面永久定格，鼠标键盘全失效，只能刷新。

**现在**（`src/net/LanClient.ts`）：所有发包统一走 `trySend()`——检查 `readyState`
之后，`ws.send()` 本身再包一层 try/catch。`send` / `sendRaw` / `sendInput` /
`sendSnapshot` / `onopen` 的 join 帧全部改走它，任何时候都不会抛。

顺带：
- 快照（`t: 'state'`）断线时**不再进重发队列**——陈旧增量重放会把旧差量套到新状态上；
  下一个关键帧（≤1 秒）本来就会补全。`restart` / `config` / `map` 这类控制消息仍保留短队列；
- 重连时先清空上一个 socket 留下的待发队列（那些帧属于一条已经死掉的连接）。

**验证**：`scripts/smoke.ts`「sending on a closed client never throws」——`close()` 之后
连续 40 次 `sendInput` + `sendSnapshot`，要求零异常。

## 二、根因 2：一个慢客户端拖垮全房（中继层背压）

**以前**：中继只调用 `ws.send()`，从不看对方消化掉没有。发给慢客户端的快照在内存里
无限堆积；等它缓过来，还要**按顺序重放几分钟前的几百帧**（连几百个旧音效一起放），
画面永远追不上房主。

**现在**（`server/lan-server.mjs`），每个连接两档水位（默认 64 KB / 1 MB，
可用 `createLanServer({ coalesceBacklog, slowBacklog })` 调整，测试注入小值）：

| 积压 | 处理 |
| --- | --- |
| > 64 KB | 只对**这一个**连接停止转发纯增量快照；关键帧、事件、控制消息照发。它最多一秒就从关键帧完全重新对齐，**其余玩家零影响** |
| > 1 MB | 直接 `terminate()`；客户端自动重连回原座位，靠关键帧重建（见根因 4） |

- `broadcast()` 现在**只序列化一次**再发给所有人（以前每个客户端各 `JSON.stringify` 一遍）；
- `send()`（访客输入转发等路径）也有 hard 水位兜底；
- 顺序上先判 hard 水位：已经没救的连接直接断，而不是「跳过」。

**验证**：`scripts/lantest.ts` 4 条——落后的访客跳过积压增量、仍然收到关键帧、
健康访客不受影响、彻底跟不上的连接被断开（外加服务器关闭有界）。

## 三、根因 3：房主切后台 → 全房定格

**以前**：Chromium 把后台窗口节流到 ~1 fps 甚至冻结。房主是唯一裁判，
**裁判停了整局就停了**；而 WebSocket 心跳由网络层自动应答，连接看起来完全正常，
屏幕上没有任何提示。

**现在**（三层）：
1. **桌面端根除**：`electron/main.cjs` 里 `webPreferences.backgroundThrottling = false`，
   最小化也满速模拟；
2. **访客看门狗**（`GameScene.guestWatchdog()`）：2.5 秒没新快照 →「网络不稳，等待房主数据…」；
   10 秒 →「收不到房主数据：房主可能已切到后台或离线」；数据恢复后提示「已重新连上房主」
   （每秒最多评估一次，不刷屏）；
3. **暂停明确广播**：`Snapshot.paused`，`setPaused(true)` 时立刻推一帧关键帧
   （暂停时更新循环停摆，这是唯一能带出消息的时刻），访客看到「房主已暂停」，
   恢复时看到「房主继续了」。

**验证**：`scripts/smoke.ts`「a paused host is announced to the room」。

## 四、根因 4：掉线就永久出局

**以前**：`if (this.retry < 2)`——只自动重试 2 次（≈2 秒），失败就「连接已断开」。

**现在**：指数退避 0.8s → 1.6s → 3.2s → 5s 封顶，**最多 30 次（≈2.5 分钟）**，
与服务器座位保留期（`SESSION_TTL_MS` = 2 分钟）对齐；期间一直显示
「连接中断，正在自动重连（第 N 次）…」；连上后计数归零，服务器凭 session 把
**原座位 / 原队伍 / 原坦克**还给它。超过上限才停，并明确提示「多次重连失败：房主可能已离线」。

## 五、根因 5：刷新页面炸掉整间房（座位所有权竞态）

**以前**：`unlink()` 只看「座位号还在不在」：

```js
if (!id || !room.players.has(id)) return;
room.players.delete(id);   // ← 新房主的 socket 也在这里被删掉
```

重连的客户端先把自己的新 socket 放进 `room.players['p1']`，旧 socket 的 `close`
**晚到一步**：座位号还在（新人在里面），于是把**新房主**踢出房间、`room.host = null`、
广播「房主离开」——整间房瞬间散伙，新玩家再也进不来。

**现在**：

```js
if (room.players.get(id) !== ws) return;   // 谁的 socket 谁负责
```

迟到的关闭事件伤不到任何人。顺手把恒为 `null disconnected` 的日志改成打印真实座位号。

## 六、附带修复

### A. 快照按地图 **id** 对齐（协议 v10 → v11）

快照新增 `levelId`；客机**先按 id 解析地图，下标只作后备**，并加越界保护。
背景：两台机器的自定义图库顺序可能不同（一侧导入过、一侧删过），旧版只带房主本机
**下标**，客机会加载**另一张图**——双方各打各的地图，看起来就是「卡住 / 画面不对」。
协议号 10 → **11**：1.5.3 与 1.5.4 联机会被版本锁拒绝，不会半新半旧。

### B. 服务器关闭不再挂起

`close()` 现在 `terminate()` 全部客户端 + `server.closeAllConnections?.()` 切断 keep-alive，
再加 **2 秒硬上限**。以前某个 socket 卡在关闭握手里，`wss.close` 回调永不触发，
Electron `before-quit` 和测试进程都会永远等下去。
`lantest` / `multitest` / `maptest` 结尾也加了退出守卫（`setTimeout(…, 250).unref()`），
失败路径照旧非零退出。

### C. 快照洪泛合并（客户端侧）

`LanClient.routeSnapshot()`：到达间隔 ≥ 20 ms（正常 30 Hz）→ 立即应用，零额外延迟；
间隔 < 20 ms（被节流后恢复、积压洪泛）→ 只保留**最新**一帧，洪泛结束后应用一次；
**关键帧永远优先于更旧的增量**（它是补全所有被丢弃增量的唯一手段）。

### D. 桌面端容错

局域网服务启动失败时不再因 `serverHandle.port` 空指针二次崩溃（回退 `about:blank`，
原因已经在弹窗里说过一次了）。

### E. `.gitignore`

忽略本地测试脚手架：`.testbuild/`、`.tools/`、`.npm-cache/`、`.pnpm-store/`。

## 八、真机自查（可选）

两台机器同一版开一局，依次试：
1. 房主切后台 30 秒再回来 → 访客画面继续，或出现明确提示而非静默定格；
2. 访客断 Wi-Fi 5 秒再连回 → 自动回原座位；
3. 房主刷新页面 → 房间不散伙；
4. 对局中房主按 P → 访客看到「房主已暂停」。
